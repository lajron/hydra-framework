# Provider Adapters

For canonical ownership and maintainer evidence, see the [Source Map](/project-wiki/hydra-framework/reference/source-map.md#maintainer-evidence).

Provider adapters make Hydra visible to specific AI runtimes without letting
those runtimes become the source of truth.

Hydra's canonical meaning lives under `.hydra-framework/`; provider-facing
files such as `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.agents/`, and `.codex/`
are adapter surfaces for runtime discovery. The provider-adapter contract
establishes that boundary, and the current adapter docs name the active provider
surfaces and canonical source directories.

## Canonical Adapter Tree

```text
.hydra-framework/adapters/
├── README.md
├── lifecycle/
│   └── README.md
└── providers/
    ├── README.md
    ├── claude/
    │   ├── README.md
    │   └── capability-map.yaml
    └── codex/
        ├── README.md
        └── capability-map.yaml
```

The root adapter README states the separation rule: common adapter contracts
belong under `.hydra-framework/adapters/`, while private executable mappings
and credentials belong in `.hydra-framework.local/`.

## Trust Model

Provider hooks are executable repository integration, not a sandbox. When a
provider loads the checked-in hook configuration, it invokes
`.hydra-framework/scripts/hydra.py` on prompt submission, edits, Bash output or
failures, and configured subagent starts. Review the [canonical trust
boundary](/.hydra-framework/adapters/providers/README.md#trust-boundary),
`.claude/settings.json`, and `.codex/hooks.json` before enabling a provider
session. The commands may read repository files and write ignored local state.

The Claude permission `Bash(python3 .hydra-framework/scripts/hydra.py:*)` is a
deliberately broad allowlist for all Hydra subcommands. A repository that needs
a narrower command surface should override that permission in local provider
configuration and review future command additions explicitly.

## What Lives Here

| Area | Owns | Does not own |
| --- | --- | --- |
| `adapters/providers/` | Provider policy, provider discovery paths, and capability-map rules. | Canonical skill, agent, workflow, tool, task, or knowledge meaning. |
| `adapters/providers/claude/` | Claude Code entry files, generated `.claude/skills/`, generated `.claude/agents/`, Claude capability mapping, and Claude hook/permission wiring notes. | Reusable Hydra procedures or role prompts. |
| `adapters/providers/codex/` | Codex entry files, `.agents/skills/`, `.codex/agents/`, Codex reasoning-effort mapping, and Codex hook wiring pattern. | User-local Codex model selection, authentication, or personal runtime settings. |
| `adapters/lifecycle/` | Provider-neutral hook moments and helper command names that adapters should call. | Broad reasoning, copied validation logic, or workflow policy embedded into provider files. |

Provider files may be generated, mirrored, or hand-written when a runtime needs
a physical path, but they must not become canonical framework meaning. Generated
files identify their canonical Hydra source through `.hydra-adapter*.yaml`
sidecars.

## Provider Surface Flow

See the canonical [capability export and reclaim flow](/project-wiki/hydra-framework/extending-hydra/capabilities.md#from-canonical-module-to-provider-surface).
This page keeps the provider-specific surfaces and comparison below; the
capabilities page owns the shared export/reclaim visual.

[Capabilities](/project-wiki/hydra-framework/extending-hydra/capabilities.md) owns the reusable modules. Provider
adapters own the last-mile mapping from those modules into the
runtime-specific files each tool discovers. If someone starts in the provider
directory, `reclaim` can classify that file and promote the meaning back into
the canonical capability tree for review.

The exporter currently generates provider skills and subagents from canonical
skills and agents. It does not generate wrappers for workflows or tool
capability records.

## Current Provider Surfaces

Three provider roots each hold one or more generated collections. Skills and
agents mirror the canonical modules described in [Capabilities](/project-wiki/hydra-framework/extending-hydra/capabilities.md#capability-kinds), so their mutable inventory is intentionally not repeated here.

```text
.claude/
├── agents/    generated agent wrappers and provenance sidecars
├── rules/     hand-maintained, not generated by export-adapters
└── skills/    generated skill wrappers and provenance sidecars
.agents/
└── skills/    generated skill wrappers and provenance sidecars
.codex/
└── agents/    generated agent wrappers and provenance sidecars
# curated: generated collections are shown without mutable module names
```

`.claude/rules/` is the one exception to this whole page's generated-surface
story: it is hand-maintained per `CLAUDE.md`, not written by
`export-adapters`, so `reclaim` never touches it.

Every other wrapper unit shown above -- `.claude/skills/hydra-*/`,
`.claude/agents/hydra-*.md`, `.agents/skills/hydra-*/`, and
`.codex/agents/hydra-*.toml`, each with its `.hydra-adapter*.yaml` sidecar --
is Git-ignored and untracked, generated by pattern from the provider registry
and wrapper prefix rather than hand-listed, so a provider added later is
covered with no second edit. **A fresh clone has none of them materialized.**
Run `python3 .hydra-framework/scripts/hydra.py export-adapters` before
starting a Claude, Codex, or other provider session against a new clone, or a
Hydra skill or subagent the session expects will simply be missing. `doctor`
fails, not warns, when nothing is materialized but the active profile expects
something to be.

The deeper generated files are checked mechanically: `reclaim` reports every
provider file's classification, catching any orphaned, drifted, or stale file
before it goes unnoticed.

## Ownership And Safe Deletion

Narrowing a capability profile (see
[Capability Profiles And Tags](/project-wiki/hydra-framework/extending-hydra/capabilities.md#capability-profiles-and-tags))
means `export-adapters` and `profile select` can now delete a previously
materialized skill wrapper, not only create or update one. Hydra deletes a
provider path only when it can prove ownership. A path is provably
Hydra-owned only when **all** of the following hold: it is in the ownership
index derived from currently existing canonical skills and agents; it is
absent from the newly desired plan; its wrapper directory or filename is
named exactly for its canonical source, not for whatever its sidecar claims;
its adjacent `.hydra-adapter.yaml` sidecar parses as a supported adapter
schema and agrees on provider and kind; its declared `canonical_source`
resolves, with no `..` segments, under the matching `capabilities/skills/` or
`capabilities/agents/` module; and the path passes the same filesystem
containment check applied to every create, update, and removal (refusing a
target that resolves outside the repository or through a symlinked
component). A wrapper directory is removed only whole, and only when it holds
exactly the files Hydra generated; anything else found inside is kept and
reported rather than partially emptied. Any surface that fails one of these
conditions is reported as `orphaned`, `drifted`, or `stale` and is never
machine-removed.

**Hydra never automatically deletes a stale wrapper.** When a canonical skill
or agent is deleted or renamed, its old wrapper leaves the ownership index
and can never satisfy the conditions above again; `reclaim` and `validate`
report it as `stale` with the exact `rm` command to remove it by hand. This
is deliberate: the ownership proof above is the safety property the whole
deletion path rests on, and a second, weaker path to delete a stale wrapper
would undercut it for a small convenience. Delete a stale wrapper yourself
once its canonical source is confirmed gone.

## Provider Differences

Claude and Codex share the same canonical skill and agent inputs, but their
adapter outputs differ because their runtimes discover different file formats.

| Provider | Generated skill surface | Generated agent surface | Mapping rule |
| --- | --- | --- | --- |
| Claude Code | `.claude/skills/<name>/SKILL.md` plus `.hydra-adapter.yaml` sidecar. | `.claude/agents/hydra-*.md` plus `.hydra-adapter-hydra-*.yaml` sidecar. | `capability-map.yaml` maps Hydra capability classes to Claude model aliases and effort budgets to Claude effort values. |
| Codex | `.agents/skills/<name>/SKILL.md` plus `.hydra-adapter.yaml` sidecar. | `.codex/agents/hydra-*.toml` plus `.hydra-adapter-hydra-*.yaml` sidecar. | `capability-map.yaml` maps effort budgets to `model_reasoning_effort`; capability classes stay unresolved so agents inherit the local configured model. |

Capability maps also record the provider version when it is known and the date
of the last compatibility verification. Those fields describe provider
evidence, not Hydra's own build status. `doctor` and `validate` report a
verification note and flag evidence older than 30 days for rechecking; a stale
note is advisory and does not claim that the integration is broken.

## Lifecycle Hooks

Lifecycle adapters describe common moments such as prompt routing, post-edit
validation, token-budget checks, model handoff, pause, and blocked work. Provider
config should call the shared `hydra.py` hook commands instead of copying
routing, validation, or token-efficiency logic into provider-owned files.

Current provider-neutral helper commands include:

```bash
python3 .hydra-framework/scripts/hydra.py route-prompt
python3 .hydra-framework/scripts/hydra.py hook-post-edit
python3 .hydra-framework/scripts/hydra.py hook-token pre-context --budget <tokens>
python3 .hydra-framework/scripts/hydra.py hook-token command-result --command "<command>" --exit-code <code>
python3 .hydra-framework/scripts/hydra.py hook-command-output
python3 .hydra-framework/scripts/hydra.py hook-retry-guard
python3 .hydra-framework/scripts/hydra.py hook-codex-command-output
python3 .hydra-framework/scripts/hydra.py hook-codex-retry-guard
python3 .hydra-framework/scripts/hydra.py hook-subagent-start
```

Claude and Codex do not share Bash result semantics. Claude uses `PostToolUse`
on successful Bash calls to return `hookSpecificOutput.updatedToolOutput`, and
uses `PostToolUseFailure` for retry feedback. Codex uses `PostToolUse` for both
successful and non-zero Bash results; Hydra's Codex output hook replaces only
large successful reviewed-family output with `continue: false` feedback, while
the Codex retry hook handles non-zero results and emits feedback only when a
session-scoped failure fingerprint reaches the retry threshold.

## What It Uses / How To Use It

### Bootstrap A Fresh Clone

Run this before starting a provider session against a clone that has not
exported adapters yet -- generated adapters are untracked, so this includes
every fresh clone:

```bash
python3 .hydra-framework/scripts/hydra.py export-adapters
```

With no `profiles.yaml` adopted, or with the checkout's active profile left at
`full`, this materializes the same full catalog a clone got before profiles
existed. `doctor` fails, rather than warning, if this step is skipped and the
active plan is non-empty. CI runs this as its first step, before `selftest`
or `doctor`, for the same reason.

### Regenerate Provider Surfaces

Use this after changing canonical skills, agents, or provider capability maps:

```bash
python3 .hydra-framework/scripts/hydra.py export-adapters --dry-run
python3 .hydra-framework/scripts/hydra.py export-adapters
python3 .hydra-framework/scripts/hydra.py validate
```

`--dry-run` reports what would be created, updated, or removed without
writing files. Plain `export-adapters` writes missing or stale generated
files and removes any wrapper unit that is no longer desired and passes the
ownership proof (see
[Ownership And Safe Deletion](#ownership-and-safe-deletion)). `validate` then
checks the framework state, including capability-map coverage.

### Check Adapter Drift

```bash
python3 .hydra-framework/scripts/hydra.py export-adapters --check
```

This is a local developer command, not a CI gate: generated adapters are no
longer tracked, so there is nothing committed for a clean clone to drift
against, and CI instead bootstraps adapters itself (see
[Bootstrap A Fresh Clone](#bootstrap-a-fresh-clone)) and gates on
`reclaim --fail-on-findings` for unmanaged surfaces. `--check` exits cleanly
only when every generated surface in the current plan is present and up to
date; otherwise it prints the paths and tells the operator to run
`hydra.py export-adapters`.

### Classify Provider-Native Files

Run this when a teammate or runtime adds files directly under `.claude/`,
`.agents/`, or `.codex/`:

```bash
python3 .hydra-framework/scripts/hydra.py reclaim
python3 .hydra-framework/scripts/hydra.py reclaim --fail-on-findings
```

`reclaim` classifies provider files as `generated`, `orphaned`, `drifted`, or
`stale`. `--fail-on-findings` makes unmanaged, drifted, or stale files a
non-zero gate.

### Promote Hand-Authored Provider Files

Use promotion only after reviewing that the provider-native file contains
meaning that belongs in Hydra:

```bash
python3 .hydra-framework/scripts/hydra.py reclaim --promote
python3 .hydra-framework/scripts/hydra.py export-adapters
python3 .hydra-framework/scripts/hydra.py validate
```

`reclaim --promote` moves orphaned provider skills or agents into
`.hydra-framework/capabilities/`. Promoted metadata is marked
`certainty: inferred` and `scope: repo-local`, so a reviewer still needs to
confirm the canonical module before treating it as stable framework behavior.
